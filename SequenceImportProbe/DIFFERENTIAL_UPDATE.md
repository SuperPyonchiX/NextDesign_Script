# シーケンス図の差分更新方針

目的は、前回PlantUML・今回PlantUML・現在の図を比較して更新しながら、変更のないモデル・関連・図形のIDと属性を保持して保存時のGit差分を抑えること。全体置換を差分更新の代替として自動実行しない。

## 対応付け

既存図との初回対応付けと、対応付け後の更新を分ける。PlantUMLへ識別子コメントを加えず、前回入力とNext DesignのIDを別ファイル（.ndmap.xml）に保存する。元ファイルを書き換えない。

初回は種別・送受信先・本文・所有階層から候補を絞る。候補が複数ある場合は出現順だけで断定せず、対応候補を提示して確定する。確定した対応はプロジェクトと図のIDにひも付け、更新後に保存する。別プロジェクトの同名図へ流用しない。

## 反映する差分

| 変更 | 処理 |
|---|---|
| 同一内容 | 更新APIを呼ばない |
| 本文・条件の変更 | 対応する属性だけ更新 |
| 追加 | 追加分だけ新IDを生成 |
| 削除 | 不要要素と関連だけ削除 |
| 順序・所属変更 | IDを保持して関連・順序・必要な配置を更新 |

保持する要素の外部関連は残す。削除対象の要素につながる関連は削除してよいが、関連先の外部モデルは削除しない。レイアウトは影響範囲だけ調整し、無変更部分へ既定座標を再適用しない。

更新前に差分を表示し、実行直前に取得時から対象が変化していないか照合する。削除・更新・追加を一つのトランザクションに入れ、失敗時は取消と読戻し照合を行う。取消失敗時は成功と扱わない。プロジェクト保存はユーザー操作とする。

## 検証と未解決事項

1. UPDATE003: 一時図で部分JSON追加・単一要素削除・既存ID保持・取消を確認する。0.5.3に実装済み、実機未確認。
2. 対応付け: 同文メッセージ、改名、移動、入れ子、コピーした識別子の重複、図側の並行編集をテストする。
3. 無変更で更新API呼出ゼロ、属性1件変更で対象ID維持を確認する。
4. メッセージ・実行区間・フラグメント・Note・ref・破棄点の追加削除を種類ごとに確認する。部分JSONの省略が保持を意味するかは推測せず実測する。
5. 保存前後の実ファイルをGitで比較し、Undo/Redo・保存再読込でも検証する。

0.5.2で用いた通常のモデル削除はシーケンス図の編集制約で失敗した。公式SDKの編集可否検査を一時停止するスコープは確認できるが、その利用による構造・描画の整合性は未検証。UPDATE003が成功しても、全要素種別に一般化せず段階的に実証する。

## 0.6.0の実装範囲

初回は更新前のPlantUMLと表示中の図を対応付ける。参加者は名称、メッセージは種別・送受信先・本文で照合する。同じ候補が複数ある場合は図内のY位置と前後のメッセージを提示して選ぶ。参加者が一意にならない場合は停止する。

本文差分更新は、構造が変わらない入力のメッセージNameだけを変更する。無変更時はモデル更新・トランザクション・対応表更新を行わない。0.6.0では図側の変更を停止理由にしていたが、この制限は0.6.1で撤廃した。図IDは照合し、今回の対象を選び直すことなく別図へ流用しない。全体置換には移行しない。

構造の変化、メッセージの追加削除、既存の別メッセージ名への変更は停止する。本文と位置を同時に変えた入力を意図まで推定することはできないため、この版ではメッセージを移動せず、本文だけ編集する。実行前に変更前後を確認する。

対応表は選択した場所へ作成する。社内の設計本文とモデルIDを含むため、この公開リポジトリへ追加しない。社内プロジェクトでGit管理する場合は、その管理ルールに従う。PlantUMLだけをAIへの入力に使えば、対応表の情報はコンテキストへ入らない。

更新前に次の対応表を.pendingへ書いて検査し、モデル更新・照合・確定後に本体へ置き換える。前回分は.bakに残す。確定後にファイル置換が失敗した場合は.pendingが残るため、次回それを選択する。モデル取消後は旧対応表を維持する。Undoや保存せず終了した場合は対応表と図が不一致になるので、図と一致する.bakを選ぶか、対応表を作り直す。

初回対応付けと本文差分更新の実機検証、保存後のGit差分確認は未実施。追加・削除・移動や他要素の差分反映は後続の実装範囲。

## 図側の編集と競合

図側の変更は通常の運用として扱う。前回入力との状態ハッシュ不一致だけでは停止しない。実行開始後、確認画面を開いている間の変更は別扱いで、計画の前提が変わった場合は書込みを行わない。

| 前回入力からの変更 | 反映方針 |
|---|---|
| 図側だけを変更 | 図の変更を保持 |
| PlantUML側だけを変更 | 変更属性だけ反映 |
| 両側で同じ属性を異なる値へ変更 | PlantUMLを優先して続行 |
| 両側で同じ値へ変更 | モデルを書き直さず対応表を更新 |
| 配置だけを図側で変更 | 現在の配置を保持 |

0.6.1はこの方針をメッセージ本文の更新に実装する。前回入力と今回入力の差分だけを現在のモデルIDへ適用する。既存の対応表はそのまま使用できる。現在の図を基準に更新後の照合値を作るため、図側だけの変更を前回状態へ戻さない。

構造差分の統合は未実装。実装時は図側で追加された管理外の要素を残し、図側で削除・移動された要素とPlantUML側の変更を個別に照合する。対応付けできない部分の再作成も影響範囲を限定し、図全体を自動置換しない。
