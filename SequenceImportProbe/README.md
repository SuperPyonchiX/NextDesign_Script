# シーケンス生成実験 0.8.59

Next Design V3.1.9向けのC#スクリプト拡張。PlantUMLからの新規図生成と、対応表を使った既存図のメッセージ本文更新・削除を扱う。本文更新・メッセージ削除・空のアクティベーションバー整理は実機確認済み。

## 0.8.59: フラグメントのサンプルに activate を明示する

事前判定が原因を出してくれた。

```
実行区間削除候補: 4 / メッセージ削除候補: 1 / オペランド削除候補: 1
L4 受信実行区間なしの書込み表現が未確定です。
L5 受信実行区間なしの書込み表現が未確定です。
L0 フラグメントの中にexecutionがあるため対象外です。
```

**製品は activate を書かなくてもメッセージごとに実行区間を作る。**だから activate のない .puml を「更新後の姿」として指定すると、モデルにある実行区間を全部消し、メッセージの受信先を無くす差分になる。後者は未解決の項目なので停止する。サンプルの作りが間違っていた。

両方のファイルに activate を明示してモデルと揃えた。枠をまたぐ区間も作らない。

あわせて、フラグメントの中に実行区間があっても、それが一緒に消えるなら受け付けるようにした。中身ごと消えるという条件は変えていない。今回の対象はフラグメント・オペランド・メッセージ・実行区間の4件。

## 0.8.58: オペランドの型IDを導出する

採取した値が答えを教えてくれた。

```
相互作用  d533e18c-…-d6c874014d84
分岐      d533e18c-…-d6c874014d84_Operand
```

**オペランドの型IDは、相互作用クラスのIDに `_Operand` を付けたもの。**独立したメタクラスではないので、クラス一覧にもパッケージ木にもビュー定義にも現れない。5つの探索経路がすべて空振りしたのはこのためで、探し方の問題ではなく、探しても無いものを探していた。

見本があればその型を使い、無ければこの規則で組み立てる。固定値を書く必要はない。導出した場合は IClass が得られないため、型の検査対象からは外れる。

これで**見本ゼロでもフラグメントを取り込める**見込み。

あわせて、診断の「会社PC内の〜」という文言をやめた。通常の開発でそのような出力はしない。

## 0.8.57: 型IDをソースに固定できるようにする

メタクラスIDはプロファイル固定なので、ソースに書いてしまえば見本は一切要らない。そのための表を用意した。

```csharp
static readonly string[] Pinned = {
    // "分岐", "00000000-0000-0000-0000-000000000000",
};
```

ラベルとIDを並べるだけ。値が入っていれば、図にもビュー定義にも見本が無くてもそれを使う。使う前に、そのIDが実在し・具体型であり・宣言された抽象型を継承していることを確認する。合わなければ無視して次の手段へ進むので、別プロファイルへ持ち込んでも誤作動しない。

**まだ値が入っていない。**オペランドの具体型IDを一度も取得できていないため。そこで、解決できた型を診断へ出すようにした。

```
Resolved types (label / id / full name):
  相互作用	d533e18c-…
  複合フラグメント	…	…
  分岐	…	…
```

見本のある図を開いて一度取り込めば、この行に全部出る。その値を Pinned へ書けば、以後は見本ゼロで動く。

解決の順序。

1. 開いている図にある同種要素
2. ビュー定義が宣言する型
3. 所有側フィールドの具体型
4. プロジェクト内のどこかにある同種要素
5. 解決済み具体型と同じメタモデルのパッケージ木
6. **Pinned に書かれたID**
7. 記録済みのID
8. プロファイル内の派生クラス

## 0.8.56: 一度解決した型を覚えて使い回す

メタクラスIDは動的に変わるものではない。毎回たどる必要はなく、**一度どこかで解決できたら記録して以後それを使えばいい**。

解決に成功した型を `%LOCALAPPDATA%\NextDesign.SequenceSync\types\<view definition id>.txt` へ記録する。1行1件のタブ区切りで、手で編集してもよい。ビュー定義ごとに分かれるので、別プロファイルへ取り違えて適用することはない。

読み戻すときは、そのIDが**実在し・具体型であり・宣言された抽象型を継承している**ことを確認してから使う。確認に落ちたら無視して次の手段へ進む。誤った型のまま進むのが一連の原因だったので、そこは必ず検査する。

IDを拡張機能のソースへ直接書く案もあるが、あれは御社プロファイルのメタデータなので、`AGENTS.md` の「会社固有のメタデータを追跡対象へ転記しない」に当たる。実質同じことを、Git管理外のローカルファイルで行う。

あわせて探索先を見直した。`AllClasses` はプロファイル側のクラスを列挙するもので、製品同梱のメタモデルは含まれないと考えられる。解決済みの具体型から `IClass.Owner` でルートパッケージまで遡り、そのパッケージ木を探す経路を追加した。

解決の順序。

1. 開いている図にある同種要素
2. ビュー定義が宣言する型
3. 所有側フィールドの具体型
4. プロジェクト内のどこかにある同種要素
5. **解決済み具体型と同じメタモデルのパッケージ木**
6. **記録済みのID（検査付き）**
7. プロファイル内の派生クラス

## 0.8.55: 見本をプロジェクト全体から探す

プロファイルのクラス一覧にも、オペランドの具体サブクラスは無かった。型の定義を辿る方向はここで打ち切る。

確実に機能している経路は最初からひとつある。**図にある実物のメタクラスを読むこと。**0.8.50 で見本のある図を開いて取り込めたのがそれ。問題は探す範囲が「いま開いている図」だけだったこと。

範囲をプロジェクト全体へ広げた。DesignModel 配下の全モデルから、その抽象型を継承する具体型を持つ要素を探す。実プロジェクトなら alt はどこかの図にある。開いている図に無くても構わない。

優先順位。

1. 開いている図にある同種要素
2. ビュー定義が宣言する型
3. 所有側フィールドの具体型
4. **プロジェクト内のどこかにある同種要素**
5. プロファイル内の派生クラス

**今すぐ使う方法:** alt を含む図を開いてから取り込めば、0.8.50 の時点から動いている。0.8.55 はその「開いておく」手間を無くすもの。

## 0.8.54: 抽象型からプロファイルの派生クラスを探す

所有側フィールドの型も抽象だった。オペランドは、ビュー定義に種別が無く（単独配置できないため）、フィールド宣言も抽象。図に実物が無い限り、これまでの経路では決まらない。

プロファイルそのものを見る経路を足した。`IProject.Profile.Metamodels.AllClasses` から、その抽象型を継承する具体クラスを探す。候補が1件ならそれを使い、複数なら名前を列挙して停止する。

優先順位は4段になった。

1. 図にある同種要素の型
2. ビュー定義が宣言する型
3. 所有側フィールドの具体型
4. プロファイル内でその抽象型を継承する唯一の具体クラス

どれも決まらないときは、宣言型の名前もエラーに載せる。

## 0.8.53: オペランドの型は所有側のフィールドから取る

0.8.52 で基本型の解決は通った。診断に `Base types from view definition:` と7件のGUIDが出て、E104 は解消した。

次に止まったのはオペランド（分岐）の型で、エラーがビュー定義の種別名を列挙してくれた。

```
Constraint, Destruction, ExecutionSpecification, Fragment, Frame, InteractionUse,
Lifeline, LifelineMapping, MappingTextLabel, Message, MessageEnd, MessageMapping,
Note, NoteAnchor, SequenceTextLabel, StateInvariant
```

複合フラグメントは `Fragment`、ref は `InteractionUse`、Note は `Note`、メッセージ端は `MessageEnd` で当たっていた。**オペランドに相当する種別だけ無い。**単独で配置できる要素ではないので、定義に出てこない。

そこで最後の手段を足した。具体型が決まったフラグメントクラスの `Operands` フィールドが指す型を使う。ただし**抽象型でない場合だけ**採用する。抽象型のまま進むのが今回の一連の原因だったので、そこは踏まない。

同じ最後の手段を、フラグメント・ref・Note・メッセージ端にも付けた。優先順位は「図にある同種要素 → ビュー定義 → 所有側フィールドの具体型 → E121で停止」。

## 0.8.52: 基本型もビュー定義から引く

見本のない図で試したら、フラグメントより手前で止まった。

> E104: 異なるライフライン間の同期メッセージがある図を開いてください。

見本依存はフラグメント等の任意要素だけの話ではなかった。相互作用・枠・ライフライン・実行区間・メッセージという**基本型も、開いている図の見本メッセージから取っていた**。条件は「同期・送信者と受信者が別・送受信ポートがいずれも実行区間」で、活性化のない図は該当しない。ゼロから作る場合は当然に止まる。

見本メッセージが無いときの経路を足した。相互作用は開いている図のモデル型から、残りはビュー定義から引く。**見本メッセージがある場合の経路はそのまま**で、これまで確認できた取込・差分更新の挙動は変わらない。

見本がない経路では、実在するメッセージの MessageSort 値を読む検査（E108）だけ飛ばす。読む対象が無いため。型の側の検査（E106、E107）は両方の経路で行う。

## 0.8.51: 具体型をビュー定義から引く

0.8.50 の検査は正しかったが、見本のある図を開かないと取り込めないのは実運用で通らない。ゼロから図を作るときに何もできなくなる。

破棄メッセージだけは以前から別の解決をしていた。`diagram.EditorDefinition.Elements` の `Type` と `ModelClass` を見て、**ビュー定義が宣言している具体型**を選ぶ。ビュー定義はエディタが配置できるクラスを列挙しているので、その要素が図に1つも無くても型が決まる。

同じ経路を複合フラグメント・オペランド・ref・Note・メッセージ端へ広げた。優先順位は、

1. 図にある同種要素の型（これまでどおり。確認済みの経路を変えない）
2. ビュー定義が宣言する型
3. どちらも無ければ E121 で停止

3 のとき、**ビュー定義に実在する種別名を一覧してエラーに載せる**。こちらが想定している名前（CombinedFragment、InteractionOperand など）と実際の語彙がずれていても、1回の実行で正しい名前が分かる。

## 0.8.50: 複合フラグメントにも型の見本を要求する

`02-fragments.puml` も同じ E122 で失敗した。過去に取込成功が記録されているファイルなので、入力の書き方は無関係だった。**0.8.48 と 0.8.49 に書いた原因の説明は2つとも誤りで、撤回する。**

診断のメタクラス表記が答えだった。lifeline / message / execution はいずれも GUID なのに、fragment と operand だけ `System.Behavior.Interaction.CombinedFragment` / `InteractionOperand` という名前表記になっている。これは抽象側のフォールバック型。

取込時の具体型は、そのとき開いている図に同種の要素があればその型を使い、無ければ抽象型へ落ちる実装だった。抽象型のままモデルは作られるが、製品は図形を作れない。それが `n/0` の正体。ref と Note には見本がないときに E121 で止める検査があるのに、複合フラグメントとオペランドには無かった。

同じ検査を入れた。見本がなければ、分かる言葉で止まる。

> E121: 型の見本が必要です。複合フラグメント（alt/opt/loop等）がある既存の図を開いてから取り込んでください。

**フラグメントを含む入力を取り込むには、alt などを含む既存の図を開いた状態で実行する。**ref や Note と同じ制約。

## 0.8.49: フラグメントのサンプルを確認済みの形へ揃える

0.8.48 の空 alt も同じ E122「複合フラグメント: 1/0」で止まった。**0.8.48 で書いた「実行区間の跨ぎが原因」という解釈は誤り。**跨がない形でも同じになる。

## 0.8.48: フラグメントのサンプルを取り込める形に直す

0.8.47 のサンプルは取込の段階で止まった。構造更新ではなく「PlantUML取込」の読戻し照合で、理由は E122「複合フラグメント: 1/0」。モデルは作られるのに枠の図形が返らない。alt を実行区間が跨ぐ形だったため。READMEにある「分岐をまたぐ実行区間の開始/終了は未対応」に当たる。実測で裏付けが取れた。

サンプルを、実行区間を閉じてから空の alt を置く形へ変えた。削除対象はフラグメントとオペランドの2件。

あわせて、要素を消すと巻き添えで変わる実行区間の境界（startAfter / endBefore）を無変更として受け流すようにした。この2つはPlantUML解析側が近傍の事象から作る補助情報で、モデルに対応する項目がない。境界以外が同一で、かつ消えた参照先がこの計画で削除される要素である場合に限る。別の残る要素へ移った場合は従来どおり停止する。

## 0.8.47: フラグメントの削除

複合フラグメントを、オペランドと中のメッセージごと消せるようにした。新しい座標は作らないので、これまでの削除の仕組みがそのまま使える。

受理条件は「中身ごと消えること」。フラグメントの下にある要素をすべてたどり、ひとつでも期待状態に残っていれば停止する。残すなら相互作用の直下へ移す必要があり、それは要素の移動として別に扱う。中にあってよいのはオペランドとメッセージだけで、実行区間や Note が入っていれば対象外。

オペランド単独の削除も受け付けない。フラグメントごと消える場合の一部としてだけ扱う。

あわせて、削除後のエディタから図形を外す処理を、決め打ちの配列名ではなく全ての図形配列に対して行うようにした。フラグメントとオペランドの図形もこれで外れる。

サンプルは `samples/structure-fragment-before.puml`。`structure-batch-after.puml` を指定すると、alt 枠とオペランドと中の `guarded()` が消える。対象は3件。

**確定もできる。**照合は試行と同じ厳密さ。

## 0.8.46: 退避データを取れない状態をもれなく捕まえる

0.8.45 のメッセージ追加は試行が成功した。続けて確定を押すと、0.8.44 で入れたガードをすり抜けて退避データの取得で止まった。

`IProject.HasUnsavedChanges()` は、プロジェクトがダーティでも保存対象の変更がなければ false を返す。試行して戻した直後がまさにこれで、内容は元に戻っているのにダーティ状態は残る。一方 `ExportModelUnit` はダーティ状態そのものを見て拒否する。

判定に DesignModel の `IsDirty` を加え、さらに取得の失敗そのものを捕まえて同じ案内へ寄せた。どちらの経路でも次の一文が出る。

> S220: 退避データを取得できません。プロジェクトを保存してから実行してください。試行して戻した直後も保存が必要です。この操作は自動保存しません。

**試行して戻したあと確定する場合は、間に保存を挟む。**確定は試行なしで直接実行してもよい。中で同じ照合をして、不一致なら取り消す。

## 0.8.45: メッセージの追加

入力にあって図にないメッセージを 1 本追加できるようにした。受理条件は次のとおり。

- 所有先が相互作用の直下で、**最後**のメッセージであること。途中への挿入は後続を下へ動かすことになるので対象外。
- 送信者・受信者が既存の参加者で、送受信の実行区間がそれぞれ 1 件。図外との送受信は対象外。
- 同じ種別（sync / async / reply）の既存メッセージがあること。それを見本にしてメタモデルと図形の項目を複製する。

縦位置は直前のメッセージから 50 下。生成器の間隔と同じ。**その位置が送受信両方の実行区間の範囲に収まる場合だけ**受け付ける。収まらなければ停止理由にする。区間を伸ばすとか後続を動かすのは別の差分として扱う。

関連は端点から先に送る。SendMessage、ReceiveMessage、その後に相互作用への所属。実行区間のときに分かった規則と同じ。

サンプルは既存の 2 本を逆向きに使う。`structure-message-after.puml` の図に `structure-batch-after.puml` を指定すると、`secondDone()` が戻る。

## 0.8.44: 未保存の変更があるときは着手前に止める

0.8.43 のメッセージ削除が停止した理由は、差分の中身ではなく退避データの取得だった。事前判定はメッセージ削除候補 1 で正しく出ている。

```
ExtensionInvalidOperationException: エクスポートするには、先にプロジェクトを保存してください。
  at ProjectUnitManagerImpl.ExportModelUnit
  at SequenceEditorCapture.Read
```

退避データは `ExportModelUnit` で取るが、これはプロジェクトに未保存の変更があると実行できない。取込や確定の直後に保存せず次の操作をすると再現する。

`IProject.HasUnsavedChanges()` で着手前に判定し、何もしないうちに案内するようにした。自動保存はしない。

**構造更新系のボタンを押す前にプロジェクトを保存する。**これが正しい手順。

## 0.8.43: メッセージの削除

入力から消えたメッセージを、差分同期のトランザクションで消せるようにした。座標を新しく作らないので、実行区間の削除と同じ仕組みがそのまま使える。

受理条件は、期待状態のどこからも参照されないことと、退避データの関連が `___Interaction_Message` ・ `SendMessage` ・ `ReceiveMessage` の 3 本だけであること。Note が紐づいているメッセージや、実行区間の境界に使われているメッセージは停止理由になる。

残ったメッセージや実行区間の座標は動かさない。消えた分の隙間はそのまま残る。縦を詰めるのは別の差分として扱う。

サンプルは `samples/structure-message-after.puml`。`structure-batch-after.puml` から `secondDone()` を抜いただけ。

## 0.8.42: 参加者の変更を確定できるようにする

0.8.41 の試行が全段階一致したので、参加者を含む計画を「接続変更・削除を確定」へ出した。確定前の照合は試行と同じ厳密さで、不一致なら取消する。

2つの確定ボタンの使い分けをはっきりさせた。

| ボタン | 対象 |
|---|---|
| 区間削除を確定 | 未使用実行区間の削除**だけ** |
| 接続変更・削除を確定 | 受信接続変更、実行区間の追加削除、参加者の追加削除。削除だけの計画は受けない |

S231 の文言も、何が対象外なのか分かる形へ直した。

## 0.8.41: 参加者の追加と削除

4. UPDATE002でID・要素・図形の照合結果を確認し、図を開き直して表示を確認する。

子要素と外部モデルとの関連も解除して置き換える。クラスや操作などの外部モデル自体は削除対象に含めず、更新後に存在を照合する。新しい子要素への関連の張り直しは行わない。図本体の関連は更新後にも照合する。削除と再取り込みは同じトランザクションに入れ、不一致や例外では取消を試み、旧モデルの名前・関連・図形IDの復元を診断に記録する。自動保存はしない。`before.txt` は診断用の構造記録で、単独で復元できるバックアップではない。

実機で確認済みなのは0.4.0の一時図に対する同一IDの名称更新と、一時モデルを含む取消まで。0.5.2の子要素削除・追加、既存エディタへの反映、外部参照保持、保存再読込、Undo/Redoは実機未確認。

「更新APIを検証」は従来どおり、一時図で同じIDへの名称更新を試し、最後に取り消すUPDATE001を実行する。既存図の更新には「現在の図を更新（実験）」を使う。

## 配置と操作

1. `git pull` 後、`SequenceImportProbe` フォルダを他の拡張と同じ `extensions` フォルダへコピーする。ZIPの展開やビルドは不要。
2. Next Designを再起動する。
3. **コピーしたプロジェクト**を開く。異なるライフライン間の同期メッセージがある既存シーケンス図をメインエディタに表示する。
4. 「シーケンス生成実験」タブの「PlantUMLを取り込む」を押す。
5. まず同梱の `samples/01-async.puml` を選ぶ。コピーであることの確認後、ログの保存先を選ぶ。
6. 取り込み件数を確認して実行する。JSONやIDの入力は不要。
7. 元の図と同じ親の配下に追加された `Async sample` を開く。結果画面と新しい図のスクショを渡す。
8. 順に `02-fragments.puml`、`03-ref.puml`、`04-note.puml` を試す。個別に動いたら `05-all.puml` で混在を確認する。サンプルの書き換えは不要。
9. 実行区間・自己呼び出し・返信は `06-activation-self-reply.puml` で検証できる。実際のUTF-8 PlantUMLファイルも同じ操作で選べる。

「最小図を生成」も残している。PlantUMLからの生成で問題が出たときに、最小構成との比較に使える。

停止したら結果画面を渡す。原因の説明が足りない場合は「診断表示」で詳細を開ける。詳細にはプロファイルの属性名やIDが含まれる場合がある。ファイルを編集する必要はない。

失敗後は保存せずに検証用コピーを開き直してから再実行する。取消APIが正常終了しても、プロジェクト全体の復元が確認できたとは扱わない。

| 複合フラグメント | `alt / else / end`、`opt`、`loop`、`par`、`break`、`critical`、`group`。条件・分岐と入れ子を生成。対応する演算子がプロファイルにない場合は実行前に停止 |
| 相互作用の利用 | `ref over A, B : 本文`、複数行の `end ref`。この版は枠と本文のみで、別の図への参照先は設定しない |

UTF-8、1ファイル1図、300KB以下、参加者1〜50本、要素500件以下、入れ子8段まで。`@startuml` と `@enduml` が必要。左向き矢印、include、上表以外の表示設定・装飾指定などは未対応で、行番号を表示して停止する。未対応行を飛ばして図を作ることはしない。`activate/deactivate` は図内または各分岐内で対応させる。`loop` の境界をまたぐ開始・終了は扱う。`destroy` は対象の実行区間をまとめて閉じる。alt等の分岐をまたぐ実行区間の開始・終了や、色付きactivateはこの版では扱わない。

現在の図の型・構造関連・列挙値を取得し、新しいIDのモデル・関連・シェイプを生成する。`BeginUndoTransaction(false)` 内で `IProject.ImportUnitFromJson` を呼び、APIの警告・エラーがなく、読戻し照合が通った場合に確定する。Note本文がRichTextの場合は、同じトランザクション内で `SetRichTextField` を使って設定する。

照合するのは図の所属・名前、ライフラインとメッセージのシェイプ数、送受信先・種別・本文・実行区間への接続・送受信の高さ、実行区間の長さ、複合フラグメントの演算子と分岐の条件・所属・メッセージ、refとNoteのシェイプ数・本文。枠の位置や入れ子の表示、非同期矢印の見た目はスクショで確認する。API照合に成功しても、描画・Undo/Redo・保存後の再読込が確認済みになったとは扱わない。

この版は新規図への取り込み。既存図のIDや参照関係を維持した差分更新は未実装。

## 0.3.3: 終了メッセージを短い左向きに配置

根拠: [V3 IMessage の受信ポートと消失メッセージ](https://docs.nextdesign.app/extension/v3.x/api/NextDesign.Core/IMessage/)。

## 0.6.0: コメントを付けない本文差分更新

PlantUMLを変更せず、対応表（.ndmap.xml）を別ファイルで管理する。既存図のメッセージ本文だけを、ID・関連・配置を維持して更新する最初の版。追加・削除・移動、参加者・条件・Note等の変更にはまだ対応しない。全体置換は「全体置換（旧実験）」へ改称し、自動では呼ばない。

1. プロジェクトのコピーを保存し、更新対象の図を開く。
2. 「差分対応表を作成」で、現在の図に対応する**更新前**のPlantUMLを選ぶ。
3. 同じ種別・送受信先・本文のメッセージは出力順に自動対応する。対応表を社内の作業フォルダへ保存する。この段階では図もPlantUMLも変更しない。
4. PlantUMLのコピーでメッセージ本文を1件だけ変更する。識別子コメントは不要。
5. 「本文を差分更新」で更新後のPlantUMLと対応表を選ぶ。
6. 変更前後を確認して実行する。図の表示、保存前後のGit差分を確認する。自動保存はしない。

現在の図の本文とPlantUMLが同じならモデル更新APIを呼ばない。0.6.2では、前回からPlantUMLが変わっていなくても図側の本文が違えばPlantUMLへ合わせる。既存の対応表はそのまま使える。ID・関連・配置を変更せず本文だけ更新するが、図全体の意味の一致を保証する処理ではない。

ローカルでは差分判定・対応表の整合性・原子的な保存とバックアップ・公式SDKコンパイルを検証する。既存図への本文差分更新と保存Git差分は実機未確認。

## 0.6.2の確認項目

- 図側だけで本文を変更し、同じPlantUMLを再入力する。本文がPlantUMLへ戻ることを確認する。
- 図とPlantUMLで別々の本文を変更する。対応付け済みの全メッセージ本文がPlantUMLに一致することを確認する。
- 図側で配置を調整する。本文更新でその座標が変わらないことを確認する。
- 更新後に同じ入力を再実行する。本文更新が0件になることを確認する。

0.6.1の「図側だけの本文変更を残す」挙動を修正した。最終要件はPlantUMLを正として意味上の差分を反映し、同じ要素のID・配置を可能な限り保持すること。現在の実装は本文だけで、追加・削除・順序・送受信先・条件等の構造同期は未実装。配置の変更でもメッセージの順序や所属が変われば意味上の差分となるため、構造同期では保持対象と区別する必要がある。

## 0.6.3: 初回の参加者対応付け

参加者名は完全一致を優先し、一致がなければ改行・連続空白・コロン前後の空白を整えて照合する。大文字小文字、単語の区切り、コロンの個数は区別する。表示名や元のPlantUMLは書き換えない。

候補がない場合や複数ある場合は、表示名・モデル名・X位置・接続メッセージ例を提示して対応先を選ぶ。「いいえ」で次の候補へ進む。対応済みの参加者は候補から外す。全候補を断るとモデルを変更せずキャンセルする。選択した対応は後続のメッセージ照合にも使う。

完全一致・正規化後の候補件数と選択IDを診断に残す。今回の修正は初回対応付けの改善であり、構造差分の同期を追加するものではない。実機での対応表作成は未確認。

## 0.6.4: 出力したPlantUMLとのメッセージ対応付け

PlantUmlToolの出力はメッセージ図形のTextと図形側の送受信ライフラインを使う。0.6.3までの対応付けはモデルNameとモデル側の送受信先を使っていたため、表示がモデル名と異なるメッセージを照合できなかった。0.6.4では出力側と同じ表示文字列・空白正規化・矢印への種別変換・図形側の送受信先を使う。

本文更新の差分判定も表示文字列で行う。出力直後の同じ本文をモデルNameへ書き戻さない。本文を実際に変更した場合は、従来のName書込み後に表示文字列も照合する。型情報などから表示を合成する図でName変更だけでは目的の表示にならない場合は取消し、成功とは扱わない。表示を構成する複数属性の更新は未実装。

「差分対応表を作成」で出力したままのPlantUMLを選び、作成後に同じファイルで「本文を差分更新」を実行する。期待結果は本文差分なし。実機での照合成功は未確認。不一致時の診断には、入力行の種別・本文と、図側のモデル名・表示本文・送受信先を記録する。

## 0.6.5: 重複メッセージを自動確定

初回対応付けで、同じ種別・送受信先・本文の候補が複数あっても確認画面を出さない。未使用の一致候補をPlantUML出力と同じ順序（送信Y、ポートX、図形IDの順）で選び、入力の出現順に対応付ける。一度対応したモデルを別の行へ再利用しない。候補数と選択IDは診断に記録する。

出力したままのPlantUMLを基準入力とする。候補が存在しない場合の診断と、参加者名が特定できない場合の候補選択は残す。今回の変更はメッセージの重複候補確認だけが対象。既存の対応表は作り直す必要がない。

## 0.6.6: 対応表用の解析を生成用検査から分離

対応表作成・本文比較・対応表の保存と再読込には、既存図を照合するための解析を使う。分岐をまたぐactivate/deactivateなど、新規図の実行区間生成では扱えない配置も、その行を削除せず読み取る。破棄後の実行区間行も原形のまま保持する。

構文・参加者・フラグメント終端・入力上限の検査は継続する。実行区間の配置を再生成したり、妥当性を保証したりする変更ではない。本文更新では実行区間行の追加削除も構造差分として検出し、無視しない。新規図生成の検査は従来どおり。

出力したままのPlantUMLで「差分対応表を作成」を再実行し、その対応表と同じ入力で本文差分なしになるか確認する。分岐をまたぐ入力の対応表XML往復・本文比較・構造変更検出・SDKコンパイルは検証済み。実機確認は未実施。

## 0.6.7: 図側に追加要素がある場合の対応表作成

図とPlantUMLの参加者・メッセージ数が違うだけでは停止しない。PlantUMLにある要素を現在の図へ対応付け、対応表に含まれない図側の参加者・メッセージ数を結果へ表示する。モデルと図形の同じIDは二重に数えない。入力側の要素の対応先が存在しない場合は、引き続き該当要素を診断する。

対応表作成では図を変更しない。図側だけの追加要素をPlantUMLに合わせて削除する処理は未実装で、対応表作成成功は構造同期完了を意味しない。本文更新でも対応表に含まれない図側メッセージ数を表示する。

図側の追加も正本へ含めたい場合は、追加後にPlantUMLを再出力して対応表を作る。追加前のPlantUMLを正本とする場合は、そのファイルで既存要素の対応表を作成できるが、追加分の削除は構造同期の実装が必要。

## 0.6.8: 初回対応付けでも改名を差分として検出

本文の完全一致を対応付けの必須条件にしない。送受信先と種別が同じメッセージ列を、出力順に照合する。一致する本文を優先しながら、改名と図側への途中追加を列全体で対応付ける。同点では先の出現を選ぶ。名前が違うという理由だけでE163にはしない。

結果に「本文の差分を検出」の件数を表示し、診断に入力本文・図の本文・選択IDを記録する。対応表作成では図を変更しない。その対応表で本文更新を実行すると、現在の表示本文とPlantUMLを比較して更新する。

識別子のない初回照合なので、同じ経路の全メッセージを同時に改名・追加削除・並べ替えた入力から元の意図を保証することはできない。対応表が既にある場合は、再作成せずそれを使えばモデルIDで追跡できる。送受信先・種別・並びに対応する要素そのものがない場合の再作成は未実装。
