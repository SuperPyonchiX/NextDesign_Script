# クラス図同期実験 0.5.2

## 0.5.2: 型モデルの新規作成

属性・引数の型に、プロジェクトに無い名前を書いた場合、これまでは C220 で停止していた。0.5.2 では所有先クラスの型定義フィールドに名前だけの型モデルを作って参照する。DeSIDE の型定義は 10 種（`ImplementationDataType` / `StructureType` / `PointerType` / `NumericalType` / `StringType` / …）あり入力からは決まらないので、既定は `ImplementationDataType`。別の種類にしたいときは型名の後ろに `<<StructureType>>` のように書く（比較では無視される）。

```
- m_Extra : NewType                      → ImplementationDataType "NewType" を作る
- m_Point : Point <<StructureType>>      → StructureType "Point" を作る
+ Run(cfg : Config <<PointerType>>)      → 引数の型も同様
```

メタクラスは同じフィールドの既存の型定義と同じもの（無ければフィールドの型クラス）。同じ実行で同じ名前を複数回使っても 1 件だけ作る。既存の同名の型があれば作らず参照する（同名複数は停止）。所有先クラスにそのフィールドが無ければ、使えるフィールド名を列挙して停止する。

参照されている操作の削除は 0.5.1 の方針のまま停止する（参照元はシーケンス図のメッセージと実機確認）。

### 実機手順（0.5.2）

1. 原本のコピーで 17 行目の型を `std::vector<ConvertErrCodeType>` から `NewType` に変えて「更新を試行して戻す」。診断の `type 'NewType' not found: will create ...` と `created type ...` の行。
2. 別のコピーで `    - m_Point : Point <<StructureType>>` を足して試行。`created type StructureType` になるか。
3. 通ったら確定 → フォームで型が入っているか、クラス配下に型定義が増えているか → Ctrl+Z / Ctrl+Y → 保存して開き直し → 差分 0 件。

## 0.5.0: 操作の引数

PlantUmlTool は操作の引数を名前だけ `Connect(transportInfo, appName)` の形で出す（引数は `Parameter` 配下の Argument モデルで、型は出力されない）。入力の括弧の中を `,` で分けた名前の並びとして扱い、次を書けるようにした。

| 操作 | 書き方 |
|---|---|
| 引数付きの操作の追加 `+ Reset(a, b)` | Method を作った後、`Parameter` に Argument を名前順に `AddNewModelAt` / `AddNewModel` で作る |
| 既存操作の引数の変更（改名・追加・削除） | 件数が同じなら順に `Name` を書き換え、違えば余分を `Delete` し足りない分を作る |
| 引数付き操作の削除 | 操作ごと `Delete()`（引数は所有子として一緒に消える） |

Argument のメタクラスは既存の引数（同じ操作、同じクラスの別操作、プロジェクト内の順）から取り、無ければ `Parameter` フィールドの型クラス。手書きで `a : Type` と書いた場合は型モデルを名前で解決して `Type` 参照を張る（無ければ停止）。戻り値は引き続き扱わない。

### 実機手順（0.5.0）

1. 原本のコピーで操作行の直後に `    + Reset(mode, force)` を足して「更新を試行して戻す」。診断の `arguments: field=... class=...` と `created argument` の行。
2. 既存の操作の引数を 1 つ改名（例 `Connect(transportInfo, appName)` → `Connect(transportInfo2, appName)`）して試行。
3. 既存の操作に引数を 1 つ足す／消すで試行。
4. 通ったら確定 → フォームの引数一覧 → Ctrl+Z / Ctrl+Y → 保存して開き直し → 差分 0 件。

## 0.3.0: 既存クラス間の関連の追加削除

多重度やロール名の変更、片端が新しいクラスの関連は引き続き停止する。

## 0.1.4: 残った link 12/12 の原因

`_current.puml` と PlantUmlTool 出力の diff で確定した。配置先の PlantUmlTool は DeSIDE のフィールド名に矢印を割り当てている（`Children` → `o--`、`SubClasses` → `<|--`、`RelateFrom` → `<--`、`Whole` → `--*` など）。0.1.1 で既定表から外したのは誤りだったので戻した。矢印は比較しない方針のまま。

- class の入れ子: PlantUmlTool は class 系ノードの中の子ノードを、親の中括弧に入れず同じ深さに書く（クラスの中にクラスは書けない）。読取りも同じ形に展開し、container（package / component キーワード）の中だけを入れ子として扱う。
- メンバの種別: 型定義（PointerType 等）は属性として出力されるが、名前に括弧を含む（`decltype(...)`）のでテキストからは操作に見える。メンバは描画した1行の文字列で比較し、属性・操作・リテラルの種別だけの違いは差分にしない。
- 匿名フィールドの線: ラベルなしの同じ行が同じ2ノード間に複数並ぶ。区別できない行は件数の少ない方まで順に対応付け、余りだけを追加・削除にする。片側が匿名の統合線（`A -- B :  / Parent`）も2本に分解する。

## 0.1.0: クラス図調査と差分検証

クラス図は `EditorType` が `ERDiagram`（プロジェクトによっては `TreeDiagram`）で、シーケンス図の `ISequenceDiagram` のような型付きAPIがない。`IDiagram` から取れるのはノードとコネクタだけなので、クラス・属性・操作・関連の意味はモデル側のメタクラス名とフィールド名から読む。その対応表（`ClassSyncOptions`）はプロファイル依存で、実機の値はまだ記録していない。だから最初の版は「実機の値を観測する」と「読取りが出力と一致することを確かめる」の2つに絞る。

| グループ | ボタン | 動作 |
|---|---|---|
| 結果・診断 | 診断表示 / 結果表示 | 直前の実行結果を表示する |
| 調査 | クラス図調査 | 表示中のクラス図のメタモデルと図形・コネクタ・関連を出力ウィンドウ（カテゴリ `ClassImportProbe`）と診断ファイルへ書き出す。保存済みなら図の Editor JSON も退避する |
| 比較 | 差分を検証 | PlantUMLファイルを選び、表示中の図と比較して差分候補を件数表で表示する。図は変更しない |

### クラス図調査

出すもの: `EditorType`・`ViewDefinitionName`・図モデルのメタクラスと所有連鎖、ノードの座標とモデル、ノード・子・孫のメタクラス名ごとの全フィールド（種別・型・多重度・現在値）、コネクタごとの両端・`LineType`・`GetRelationsOf` の関連情報、図上のノードを結ぶ参照・所有フィールドの一覧、既定の対応表で読んだ結果と要照合項目。

プロジェクトが保存済みなら `ExportModelUnit` で図のユニットを一時ファイルへ出力し、その図の `Editors` 要素だけを `_editor.json` に残す。書込み設計に使う。未保存なら省略して続行する。この操作は自動保存しない。

### 差分を検証

入力は **PlantUmlTool の「表示中の図を出力」で出したクラス図の `.puml` を編集したもの**。解析できる文法はその出力形式に限る。

```
@startuml
title 図名
hide empty members

package "所有元" {
  class "名前" as 別名 <<ステレオタイプ>> {
    + 属性 : 型 [多重度] = 既定値
    --
    + 操作(引数 : 型) : 戻り値
  }
}

別名 --> "0..*" 別名 : ロール名
@enduml
```

- 宣言は `class` / `abstract class` / `interface` / `enum` / `entity` / `struct` / `package` / `component`。`"名前" as 別名` の形が基本で、引用符や別名のない `class Foo` も受け付ける。
- 矢印は `-->` `--|>` `..|>` `..>` `o--` `*--` `--` `..` と、左向きの `<|--` `--*` `<--` を受ける。矢印の向きは解釈せず、行の左右をそのまま関連元・関連先とする。矢印の種類は比較しない。
- 双方向の統合線（`a "1" -- "0..*" b : x / y`、または左側にも多重度がある行）は、出力側の統合規則の逆で2本の関連に分解する。前のラベルが左→右、後ろが右→左。
- `hide` / `skinparam` / `!theme` などの表示指定と `'` コメントは無視する。無視した行は診断ファイルに記録する。
- 解釈できない行、未宣言の別名、閉じ括弧の不足は `E120: N行目:` で止まる。

比較は名前で対応付ける。クラスは所有先（package か図上の親ノード）と名前・キーワード、メンバはクラス内の種類と名前、関連は両端とロール名。同じ親の中で1件だけ対応が付かない要素は改名として扱う。結果画面は種類×操作の件数表、診断表示は入力行と種類だけで、設計本文・名前・IDは実行PCの診断ファイルにしか出さない。

クラスの並びは図形の座標で決まるため、宣言順の違いは差分にしない。メンバの並び替えと所有先の変更は `move` として出す。

## 配置と操作

1. `ClassImportProbe` フォルダを他の拡張と同じ `extensions` フォルダへコピーし、Next Design を再起動する。
2. **コピーしたプロジェクト**でクラス図をメインエディタに表示する。
3. 「クラス図調査」を押す。結果画面と「診断表示」のスクショ、および出力ウィンドウ（カテゴリ `ClassImportProbe`）の全文を渡す。診断ファイルは `%LOCALAPPDATA%\NextDesign.ClassSync\reports\` に `..._probe_....txt`（同じ名前の `_editor.json`）として残る。
4. PlantUmlTool の「表示中の図を出力」で同じ図を `.puml` に出力する。
5. 「差分を検証」でその未編集の `.puml` を選ぶ。差分候補 0 件が目標。残差が出たら、診断ファイルと同名の `_current.puml`（拡張が図から書き出したPlantUML）を PlantUmlTool の出力と比較すると、読取り側のどこが違うか分かる。

診断ファイルにはモデル名・ID・設計内容が含まれる。社内の管理ルールに従って扱い、公開リポジトリへ追加しない。

## 既知の制約

- 図への反映はしない。属性・操作の本文更新、関連の追加削除、クラスの追加削除は 0.2.0 以降で、実機のメタモデル記録を取ってから段階的に検証する。
- `ClassSyncOptions` の対応表は PlantUmlTool の既定表と同じにしてある（出力と一致させるため）。未対応のメタクラスは属性、未対応のフィールドは `-->` として読み、要照合項目に出す。
- PlantUmlTool の出力と同じく、図に載っているノードだけを対象にする。自己参照は線にしない。所有関連（`IsEmbedded`）は線にしない。
- 同じ名前のメンバが1クラスに複数ある場合、対応付けは兄弟列の並びに依存する。
- 統合線の分解規則は出力側の規則の逆算なので、手書きで `A "1" -- "0..*" B : x` と書くと双方向として読む。

```powershell
python ClassImportProbe/sync/bundle.py
python ClassImportProbe/tests/run_tests.py --sdk-root work/sequence-api-research
python C:\Users\ksk01\.claude\skills\nextdesign-script-extension\scripts\validate_manifest.py ClassImportProbe --nd-version 3
```

テストは `samples/*.puml` の解析・書出しの往復（バイト一致）、差分計画の件数、画面文言、版の一致を検査する。`--sdk-root` は公式SDKに対するコンパイルで、APIの実在を確認するだけ。実機での読取り結果は保証しない。
