## 2. 0.10.0: 対象外の撤廃（配置と書き込みの一本化・実機未確認）

ユーザーの方針「統合前に未対応は全部なくす」（2026-09-25）に従い、種類ごとに積み上げていた配置と制限をやめた。

- **配置**: `SequenceRelayout`（縦）と `SequenceLaneLayout`（横）の1つの計算。図を上から「メッセージ・Note/ref・破棄・枠の開始・分岐の開始・枠の終わり」の並びにし、変更前との最長共通部分列にある要素は位置を保つ。挿入があればその分だけ下げ、削除があれば消えた要素の位置へ詰める（生成器の間隔より広くはしない）。距離は生成器の行カーソル（ガードは +30/+20、枠の下端は +8 など）の空間で測る。既存要素どうしの間隔は、元が生成器より狭くても保つ
- **バー**: 入力の `startAfter`・`endBefore`・`endContainer` を窓として位置を決める。既存のバーは、窓に収まる限り元の位置を移したもの（`Map`）を使う。受信メッセージで始まるバーは、そのメッセージとの距離を保つ。`startAfter`/`endBefore` の欄そのものがない入力（手組みのテスト）は「指定なし」として元の位置を保つ
- **枠の横幅**: 既存の枠は深さが変わらなければ元の左右を移す。新しい枠・深さが変わった枠は最上位の枠（なければレーンの端 ±16）から深さごとに 16 ずつ内側。最後に、中身（入れ子の枠・Note・ref）を囲むように広げる（読取りが Note の所属を矩形の包含で決めるため）
- **書き込み**: 所属の変更は関連の付け替え（同じ ID で SourceId を変えて取り込む）か `UnRelate`。消える分岐の関連は削除で一緒に消えるので `UnRelate` しない。図外の端（MessageEnd）の作成・削除、送信元の付け替え、種別・演算子の変更（同じ ID の再取込）、応答とバーの関連の正規化（この更新が触るバーだけ）、破棄メッセージの付け直し
- **作り直し**: 分岐を別の枠へ移す・破棄の参加者を替える は、所有関連が付け替えられないので `SyncPlan.Build` で新しい ID を振る（元は削除、新しいものを追加）
- **見本なし**: 参加者・バー・メッセージ・図外の端は、図に見本がなければ `PumlRuntime.SyncBaseTypes` の型と関連の行から作る（空の図への反映を含む）。見本がないと製品が決める寸法（参加者の見出し、バーの幅）は `LooseShapeIds` で照合から外す（存在と所属は照合する）
- **止めるもの（残り）**: 入力に activate のない参加者との送受信（「入力にない実行区間を発明しない」に従う）、要素のない分岐（製品が描けない）、送受信の両方が図外のメッセージ（解析器が受け付けない）、実行区間とメッセージの接続の食い違い（壊れた入力）
- **期待状態**: 関連の番号は、追加は両端とも末尾、付け替えは元の集合を詰めて移動先の末尾、`UnRelate` と削除は元の集合を詰める。付け替えの詰め直しは、この更新で足した関連も含めてフィールド単位で数える
- **シミュレーター**（`tests/SimulatorTests.cs`）: 生成器で before を作り、`DiagramSnapshot.Read` を真似た読取り、実行側と同じ取込・解除・削除・エディタ再取込、`SequenceStructureTrial.Read` を真似た状態で「接続変更後」「削除後」の照合、読み直した図と入力の差分0件、までを全シナリオで回す。わざと不具合を入れると落ちることは確認済み。製品が取込後に自分で配置し直す動き（応答の関連でバーを縮めるなど）は再現しない

### このスライスの制限（意図的）

- 挿入するメッセージの直前は、同じ所有先（相互作用直下、または同じオペランド）にある既存のメッセージに限る。オペランドの先頭、枠の直後への挿入は停止する
- 挿入するメッセージは既に開いているバーの間に書く。新しいバーを同時に作る挿入は対象外
- 1回の更新で挿入できるメッセージは1本
- 挿入位置より下に Note・ref があると停止（メッセージと枠だけを下げる）

### 0.9.2: 枠を含む挿入・枠の中への挿入

- 挿入位置より下の枠は `Y` ごと下げる。オペランドは枠上端からの相対値なので動かさない
- 挿入位置を含む枠は `Height` を伸ばし、挿入位置より下で始まるオペランドの `Position` を下げる
- 既存オペランドへの挿入は、図の末尾でも挿入として扱う（枠を伸ばすため）
- サンプル: `structure-fragment-before.puml` → `structure-insert-frame-after.puml`（枠の上へ挿入）／`structure-insert-inframe-after.puml`（枠の中へ挿入）
- 枠の上へ挿入は確定・保存再読込・差分0件まで確認済み（0.9.2）
- 枠の中へ挿入（`structure-insert-inframe-next.puml`）は 0.9.3〜0.9.4 で確定・保存再読込・差分0件まで確認済み
- 残り: オペランドが2つ以上ある枠で後ろのオペランドを下げる処理。`structure-else-before.puml` → `structure-else-insert-after.puml`

### 0.9.7: 生成の縦間隔と、応答の起点の調査

- 生成（PlantUML取込）のメッセージ間隔を 50 → 40 に詰めた（`PumlBuild.MessagePitch`）。同期側の挿入・追加の間隔（`MessageSpacing`）も同じ定数を使う。既存の図は間隔50のままで、挿入はそこへ40で入る

  `%LOCALAPPDATA%\DENSO CREATE\Next Design\logs\yyyyMMddHHmmss.log`
  例外の種類・メッセージ・トレース・直近のコマンド履歴が入っている。推測で候補を潰す前にこれ
- クラッシュ後は保存せずに製品を再起動してもらう

### よく効く事実（詳細は `.local/nd-knowledge/`）

- 図形表現は `Json([数値…])` に後置文字列。フラグメントは演算子名、オペランドは `Json([Guard, Position])`、ライフラインはタイムライン長が裸の数値で付く（K149〜K153）
- オペランドに矩形はなく、`Position` は枠の上端からの相対値（K149）
- 枠の矩形はライフラインの左端 -16 ／右端 +16 で製品と一致する（K151）
- バーは長さを `Height` と `Length` の両方に持つ。片方だけ書いても無視される
- 既存要素を指す関連は `TargetIndex` も数える（K156）
- 図が一度も使っていない図形コレクションはエディタJSONに存在しない。最初の1件は配列から作る（K148）
- PlantUML は直前のメッセージ以降に deactivate された参加者を、メッセージを挟まないと再 activate できない。`tests/lint_samples.py` が回帰検査で見る（K146）
